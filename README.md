## Accepted product contract

A run's subprocess scope is settled at the run boundary, not after every command. Cleanup observations, completeness of discovery, substantive answer/verdict, capture permission and release/installation are different facts. Known survivors or unreadable known identities remain unresolved. Unrelated unknown PIDs are not enrolled or signalled. Linux discovery incompleteness and the specific macOS SIP blind spot are disclosed; neither is manufactured as complete process-death proof.

The scope-aware detail API always includes `summary.processScope`: a valid compact outcome or explicit null if its record is unavailable. The record attempt is made once before terminal publication; failure does not regenerate or erase an already received answer. The companion distinguishes absent legacy fields from explicit null. Historical first-capture copies can consequently remain retained and refuse a next checking-thread turn. Windows copy-use compatibility is explicitly a weaker host policy on a narrowly defined successful/census-unsupported outcome, not proof that every detached process died.

The original454 exception preserves an explicitly completed Codex answer only when cleanup uncertainty is proof-only. Cancellation, observed survivors, mixed reasons, late root errors, interrupted/failed completions and a new root turn are not converted into success. A substantive reviewer FAIL inside a successfully completed run is not the same as failed execution.

Real account-backed Claude/Codex/Cursor acceptance on the installed chain was explicitly deferred to the general-update stage. Credential-free process, pipe, API and native-platform tests are not described as that evidence.
