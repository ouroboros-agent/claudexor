Repeated run detail reads (`GET /v2/runs/:id`, also used by MCP status/wait snapshots) can reuse the bulk worker's folded event prefix and parse only appended lines. Reuse assumes the existing append-only writer: identity changes, shortening below the retained offset or changed start/end guard bytes trigger a full fold. An arbitrary middle-only in-place rewrite can go undetected. A last record without its newline is evaluated without being consumed. Decision, telemetry, answer, reviews, task contract, artifacts and live fields remain fresh per request. Retention is limited to 32 runs and a 64 MiB accounting budget, 8 MiB per run, not an exact JavaScript heap cap; evicted or oversized folds and separate recovery/ancestry readers can still read the whole log. On paired synthetic macOS logs of 8 MiB and 200 MiB, unchanged repeated detail read 8 KiB instead of the whole file, taking about 9 ms and 10 ms rather than 48 ms and 890 ms, with byte-identical responses in the tested supported cases. MCP-shaped polling on the synthetic 200 MiB run reduced SSE delivery p99 from about 1 s to under 10 ms. These measurements are not production or cross-platform guarantees.
