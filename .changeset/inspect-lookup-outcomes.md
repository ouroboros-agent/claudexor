`claudexor inspect` now says `no such run` only when a running daemon's run registry answers 404 for the id (`code: "run_not_found"`). Before, a cross-project lookup that could not complete printed the same message, so a run started in another project could look absent while it still existed. Each other outcome returns the standard failure envelope, with its own code whenever the answer is recognized: `invalid_argument` (exit 2) for a malformed id; `daemon_unavailable` when no daemon is reachable, so runs from other projects were not checked, or when the connection drops before the whole answer arrives; the daemon's own problem code, such as `daemon_recovery_only`, a refused handshake or another 404; `invalid_service_response` for an unreadable success body or a recorded run directory outside a run store; `run_not_materialized` with the state for a run the daemon knows that has no run directory yet; and `run_artifacts_unavailable` with the state and recorded path when that directory is missing or unreadable. An error answer that is not a control problem, such as a non-daemon 404 page, has no code and names only its HTTP status. The lookup validates only the run-detail fields it uses, so additive same-major fields elsewhere in the answer are tolerated and a known problem keeps its recovery details when it carries extra fields; a run state value this CLI build does not know is still reported as `invalid_service_response`. The CLI reads exactly the directory the daemon recorded, so a job id the daemon knows now resolves to its run. A local retained run is still shown without the daemon, and the lookup still never starts one. A found run with no summary or output no longer prints that the run may not exist.
